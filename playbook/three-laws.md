# The Three Laws of interview answers

Grade every answer 1–5 on each law. An answer is strong at 12+/15 with no law below 3.

| Law | 5 looks like | 1 looks like |
|---|---|---|
| **Structure** | Signposted up front ("Two parts: the bug, then the fix"), STAR for behavioral, clarify → approach → complexity → code → test for coding, requirements → API → data model → high-level → deep dive → trade-offs for design. | Rambling chronology; the point arrives after 2 minutes or never. |
| **Specificity** | Real numbers, names of systems, the exact decision and why the alternative lost. "p99 went from 900 ms to 140 ms after we moved the fan-out to a queue." | "We improved performance a lot." "I worked with the team." |
| **Skill demonstration** | The answer proves the competency the question probes (ownership, debugging depth, trade-off thinking, communication). Says "I", not just "we". | Describes the situation but never shows what *you* did or thought. |

## Question types (SWE)
`dsa-coding` · `system-design` (lite for new grads: design a URL shortener / rate limiter / chat) · `cs-fundamentals`
(OS, DBMS, networks, OOP) · `project-deep-dive` · `behavioral` · `debugging` · `culture-motivation` · `hr-logistics`

## Rewrite rules
- Rewrites use only stories and facts from the experience library's story bank and projects.
- Show the rewrite, then one line on which law it fixes.
- If no real story fits, say so and suggest which experience to mine or which story to add.
